## Flagged Assumptions (edge-probe items resolved as inapplicable, not force-fit)

- **APP-04 adjacency**: does not apply — the picker returns a single file/folder result (or a multi-select list treated as an opaque collection), no merge/collision concept exists between picker invocations.
- **APP-04 empty/null input**: the only "empty" case is the user cancelling the dialog, which is already an explicit, tested path (Task 2 logs "cancelled" and returns null) — not an unresolved probe gap.
- **APP-04 ordering**: single-shot invocation only in Phase 1 (the debug smoke-test button); there is no queued/ordered sequence of picker calls to reason about.
- **APP-04 encoding**: `PickFileResult`/`PickFolderResult.Path` are already-resolved OS file-system paths returned by the WinAppSDK API itself; no user-supplied free text passes through this service in Phase 1, so no encoding-ambiguity surface exists.
- Concurrency (double-invoke prevention) is the one genuine edge case this domain has, and it is already covered as an explicit `must_haves.truths`/`prohibitions` entry and Task 2 acceptance criterion — not omitted, just not restated here.
