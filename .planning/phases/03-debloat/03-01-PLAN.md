<objective>
**As a** user who wants a clean, fast Windows install, **I want to** run each of the 28 PowerShell-backed debloat actions from one page and see live streamed output while they run, **so that** I can trust the app isn't frozen or silently failing while it makes system changes — with the page's logic living in a ViewModel/service, not code-behind, fixing the predecessor's `DebloatPage.xaml.cs` architecture debt (DEBLOAT-03).

This plan lands the entire Debloat architecture in one pass: the `DebloatAction` catalog model, the full 28-row/5-category static `DebloatCatalog` (all real, correct metadata — not stub data), a catalog-driven `DebloatViewModel` with generic confirmation-gated, concurrency-guarded Run/Undo dispatch, the 5-category grouped `DebloatPage.xaml`, DI wiring, and Home/nav enablement — then proves the whole vertical slice end-to-end on exactly one real action ("Telemetry — Disable") before the remaining 27 actions' scripts are embedded in Wave 2-6 plans. Per D-01, this is deliberately NOT `ITweakHandler`/`ITweakCatalog` — Debloat has no live-state read-back, so `DebloatCatalog` is plain static data (no `GetState`/`SetState`, no per-key prior-state capture) and `DebloatViewModel`'s Run/Undo commands are a generic two-method dispatch over `DebloatActionItem`, not one `[RelayCommand]` per action (RESEARCH.md's own architecture diagram recommendation, chosen over `GamingTweaksViewModel`'s one-method-per-action shape because 28 rows makes per-action methods unwieldy). Per D-11, exactly 5 of the 28 actions (BitLocker, Bloatware removal, Edge & WebView removal, Hibernation, OneDrive removal — the research-proposed classification, presented here for review) require an `IDialogService.ConfirmAsync` gate before their Run path executes.

The remaining 27 actions' `RunResourceSuffix`/`UndoResourceSuffix` values are wired into the catalog now (correct metadata) but their `.ps1` resources are not embedded until Wave 2-6 — clicking one of those rows before then is a **functionality gap** (a clean, logged, non-crashing `FileNotFoundException` catch — the exact same pattern `GamingTweaksViewModel`'s WR-04 fix already established), not an architectural gap, per the tracer-first rule that stubs are acceptable only where they can be filled without restructuring anything.

**DEBLOAT-01's "28 vs 29" scope note:** the predecessor's page has 29 buttons; "Create Restore Point" is excluded from this catalog (RESEARCH.md's "28 vs 29 Reconciliation" — it is a safety/utility action with no Undo, categorically distinct from the 28 debloat/privacy/cleanup actions, and `HomeViewModel.cs`'s existing Debloat card description already says "Run 28 PowerShell-backed debloat actions").

**Edge-probe non-applicability note (DEBLOAT-01):** the deterministic edge-probe's "adjacency" and generic "ordering" categories assume a data collection with merge/sort semantics (e.g. two overlapping ranges, a sortable list with ties). DEBLOAT-01 is a fixed, compiled-in 28-action button list — there is no merge/collide/separate question (no two actions can be "adjacent" or "touch") and no tie-breaking question (every action has a unique `Key`, so "when elements compare equal" never applies). Both probes are reasoned non-applicable rather than force-fit; the genuinely applicable slice of "ordering" (deterministic category/action display order) is captured as an explicit must_have truth above instead.
</objective>

| Confirmation dialog → destructive system mutation | `IDialogService.ConfirmAsync` is the only friction point between a user click and a D-11-classified irreversible system change |

| T-03-01 | Tampering | Embedded `.ps1` resource selection | low | mitigate | `RunResourceSuffix`/`UndoResourceSuffix` are fixed string literals in the compiled catalog, never user input — no injection surface into the `powershell.exe -File` invocation, per RESEARCH.md's V5 Input Validation finding |
