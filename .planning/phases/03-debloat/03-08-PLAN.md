<objective>
**As a** user who runs a Debloat action and then clicks Undo to revert it, **I want to** have Undo actually restore the exact registry, environment-variable, or file-permission state my Run action changed, **so that** I can trust the app's core promise — every debloat action "must apply correctly, report accurate state, and (where applicable) be safely revertible" — instead of silently believing I've undone a change that is, in fact, still active.

(ROADMAP.md's Phase 3 `**Goal:**` line is not itself written in strict "As a/I want to/so that" form — 03-VERIFICATION.md already flagged this as a stale/default field mismatch, non-blocking. This story reuses and narrows 03-01-PLAN.md's own established framing to the specific gap this plan closes, per the MVP-mode instruction to apply vertical-slice discipline without re-running a full mvp-phase pass for a bounded gap-closure round.)

This plan closes 03-VERIFICATION.md's `gaps_found` status (score 5/8) by fixing the 6 Undo scripts 03-REVIEW.md's code review (CR-01 through CR-06) and 03-VERIFICATION.md's independent re-verification both confirmed write to the wrong registry key/hive/env-var/ACL — meaning they execute successfully, print a success message, and do nothing to reverse the actual change their paired Run script made. Per CLAUDE.md's Core Value, this is a direct violation of "safely revertible," not a cosmetic bug. Each fix below applies 03-REVIEW.md's own already-reviewed diff verbatim (no new logic invented) so the fix itself carries no additional review risk.

Because the bug lives inside opaque PowerShell script text — not C# logic behind a testable interface like `ITweakHandler`/`IRegistryService` — the only test that can structurally catch this class of bug is one that runs the real script and reads real system state, which is exactly what `DebloatCatalogTests` (resource-manifest/wiring only) cannot do. This plan adds a new `DebloatScriptRegressionTests` suite that does that: real `ScriptRunner`, real `powershell.exe`, real `Microsoft.Win32.Registry`/`System.Environment`/`icacls` reads, before Run, after Run, and after Undo, with every mutation restored in a `finally` block. Because 4 of the 6 fixed pairs write to `HKLM` or a machine-scope environment variable (privileges this app itself requires per APP-01/`requireAdministrator`), those specific facts require the test process to run elevated; they detect non-elevation at runtime and skip cleanly (documented, not silent) rather than either failing the default `dotnet test` run or fabricating a false pass. The other 2 facts (folderdiscovery's `HKCU` pair, and storesearch's scratch-file ACL round trip) need no elevation and always run for real.

`storesearch`'s `RequiresConfirmation` flag is also flipped to `true` in this plan (03-REVIEW.md CR-03's second half) — its Run script applies an effectively irreversible `icacls /deny Everyone:F` and, until this plan, had a genuinely broken Undo with zero confirmation gate; now that the Undo is fixed, the missing confirmation gate is still worth closing since it directly combines with the ACL-change risk CR-03 flagged. `windowsai.ps1`'s undisclosed process-killing (03-REVIEW.md WR-04) is explicitly OUT of scope for this gap-closure plan — it is listed only as a Warning in 03-VERIFICATION.md, not one of the 4 failed truths, has no paired Run/Undo mismatch, and is unrelated to the CR-01..CR-06 bug class this plan exists to close; deferring it here is a scope decision, not an oversight.
